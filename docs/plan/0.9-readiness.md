# Plan: 0.9 production pre-release

**Status:** P0, P1 and P3 complete; P2's deterministic layers are green and the
live P2 artifact (#700/#702) is the remaining evidence gap. The maturity-gate
decisions landed in #725–#728. Release execution is #732. Tracked by epic #689
and the `0.9 readiness` milestone (issues #690–#710, plus #621).
**Scope owner:** benchmark / quality.
**Decision:** 0.9 is a production pre-release gate. 1.0 production-readiness
work starts only after it passes.

## The 0.9 claim

Amber 0.9 is the first build whose user-facing behaviour is measured end to
end on every surface it ships, whose harness cost and agentic behaviour are
pinned against a recorded live run, and whose release artifacts carry that
evidence. It is **not** a 1.0 API freeze; breaking changes remain allowed where
the upgrade note names them.

Each clause maps to evidence: "user-facing behaviour" to the capability matrix
and its journeys; "harness cost and agentic behaviour" to the hermetic gates
plus the P2 live artifact; "release artifacts carry the evidence" to
`make bench-release-check VERSION=0.9.0` and the release checklist. The
long-horizon suite is deliberately **outcome-only**: its policy client reports
no token usage, so it gates outcome, tool calls and wall time; harness-cost
claims come from the hermetic suite.

## Scope and boundary

P0–P3 make **no** version stamp, package-version bump, tag or beta-copy edit.
Release execution is P4, filed as #732 after P3 closed; a tag publishes
unattended, so it is never part of a coverage PR.

## What "full coverage" means here

A capability is covered when a **machine-checked matrix** says so, not when a
doc lists it. `tests/journey_matrix.json` is the source of truth; `BENCHMARK.md`
and `docs/spec/tui/e2e-testing.md` link to it rather than duplicating it.

The matrix (schema version 1) has a row per capability group. `sources` names
every product item the row covers, and `journeys` names the journey or the
recorded reason on each surface:

```json
{
  "version": 1,
  "sources": {"commands": "completions.json", "plugins": "tests/capability_snapshot.txt"},
  "surfaces": [{"id": "editor", "source": "tui/", "description": "the prompt composer"}],
  "capabilities": [
    {
      "id": "session.lifecycle",
      "sources": ["command:session", "command:session.save", "alias:save"],
      "journeys": {
        "cli": ["e2e-session-resume"],
        "tui": ["restart"],
        "bench": ["na: no session store in the harness"]
      },
      "notes": "The CLI journey resumes through --session; the TUI restart journey saves and restores."
    }
  ]
}
```

`tools/journey_sources.py` is the enumeration oracle. It reads
`completions.json` (every documented path and visible alias),
`tests/capability_snapshot.txt` (every bundled plugin capability and every tool
the bare-host default composition registers, generated from the live
declarations by `make capability-snapshot-update`), `menus.json` and
`keybindings.json` (TUI-only `ui.*` actions), and the three journey indexes. It
fails closed on a short scan.

`tools/journey_matrix_check.py` (CI job `journey-matrix`) enforces:

- every source appears in exactly one row, and no row names a source that does
  not exist;
- every journey cell is a journey its runner can execute, or carries
  `internal:`, `na:` or `deferred:` with a real reason;
- an alias is in its target's row, except the explicit `alias_owners` entry for
  a dynamically contributed subtree (the MCP `/plugin mcp` alias);
- the surfaces are exactly the six in `tools/journey_sources.py`.

`make journey-matrix-release` runs the same check with `--require-complete`,
which refuses every `deferred:` cell. A `deferred:` cell is the waiver: it names
the issue that closes it, and the release check is its expiry. A pty test that
renders one screen is not a journey.

## Gaps

1. **The matrix is complete for 0.9.** P0 built the source and the gate;
   102 cells are passing journeys, 22 are `internal:` and 109 are `na:` with
   their reasons recorded. `make journey-matrix-release` is green: no
   `deferred:` cell remains. Listing-derived capabilities (verbosity, Gemini
   `thinkingConfig`, #686) still have unit tests but no binary journey, and
   the direct `amber-cli skills` and web-tool cells are `internal:` where the
   one-shot journey harness cannot carry them.
2. **The inventory is one doc now.** `docs/spec/tui/e2e-testing.md` lists the
   24 CLI, 27 TUI (including `tab-switch-live`) and 5 long-horizon journeys;
   `BENCHMARK.md` links to it, and `tests/journey_matrix.json` is the machine
   view (P0.3).
3. **Live validation is stale and narrow.** The local fixed service is
   inviolate and was inactive; the only live minimum is the 0.8.9 cloud
   stand-in. Three promised validations — session brief, 32 KB tool-result
   budget on a live long read, plan/task default-on — are "re-scoped, not
   executed" in `BENCHMARK.md` and `docs/release-benchmark.md`.
4. **Maturity gates are proxies.** `bench-allow:` waives a regression for one
   reviewed PR, now dated and capped at 30 days; the last 2 additive efficiency
   cells graduated into the 48-cell baseline, and a new one needs a dated
   record; mutation testing is advisory and selection-sensitive; the TUI floor
   is the 80% project target, measured with the pty and journey harnesses.
5. **#621 is unmeasured, and recorded as such.** The macOS tab-switch freeze
   has no reproduction; `tab-switch-live` is its detector and #621 is the
   `known_unmeasured` entry in the flake budget, so a detector failure is
   budget spend rather than an accepted pass. `docs/platform-support.md`
   records the macOS tab-switch cell as manual.
6. **The long-horizon baseline has no token axis — resolved as outcome-only
   (#707).** The repo-long scenarios drive a policy client that reports no
   usage counters, so 0/0 was absence of measurement, not a measured zero cost.
   `bench_check.py` now renders those cells as `n/a (outcome-only)` and the
   baseline comment names the limit. The 0.9 harness-cost claim rests on the
   hermetic suite, not on this path.

### P2 — Release-grade live evidence

Follow `docs/release-benchmark.md`; it is the procedure, not a suggestion.

- **P2.1** (#700) Run the **current model corpus** (56 model scenarios on 2026-11-23;
  the gate floor is 49; `--cat model`) with `--repeat 3` on the fixed local
  profile if it is available. The local service
  is inviolate and is never reconfigured. If it is unavailable, use the
  configured cloud profile recorded for 0.8.9 (`deepseek-chat`) and record the
  substitution in the artifact directory and release notes.
- **P2.2** (#700) The gate's actual contract, quoted exactly: `mode: live`, engine
  version matching the tag, **≥49 scenarios**, no **unexpected** failures
  (model-quality failures must carry a reason; 0.8.9 had 14), model-score drop
  within **band 5.0** against the previous artifact on the **same (model,
  profile)**. Do not change the profile between 0.8.9 and 0.9, or there is no
  comparable band.
- **P2.3** (#701) **Done.** The gate compares the common successful corpus:
  prompt+completion tokens and tool calls within +10% (repeat medians), zero
  compaction/hard stops, and wall/TTFT pathology ceilings; the score band stays
  5.0. The bands are in `docs/release-benchmark.md` and covered by 26 gate tests.
- **P2.4** (#702) Execute the three deferred live validations (session brief, 32 KB
  tool result, plan/task default-on) or record each as not-met with a reason.
- **P2.5** (#700) Redact the artifact and check it for keys/prompts before committing;
  record the cost/approval boundary for the cloud run.
- **P2.6** (#700) Re-run policy: one planned run. A repeat needs a recorded reason
  (infrastructure failure, broken scenario, wrong binary) and both runs are
  reported; a low score is a result, not a reason to re-roll.
- **Exit:** `make bench-release-check VERSION=0.9.0` green; `BENCHMARK.md`
  records the run, its profile and its limits.

### P3 — Promote maturity gates deliberately

- **P3.1** (#703) **Done — decided advisory.** The module spike (69 mutants,
  91.3% conservative, 37% vs 91% by test selection, 6 timeouts, one equivalent
  mutant) plus the nightly changed-line samples (43/43 and 14/14, zero
  survivors) led to rejecting a per-module/changed-line survivor budget: zero
  is a cliff with a known equivalent mutant, the score is a statement about
  test selection, timeout classification moves, and one mutant runs the whole
  suite. `tests/gates/test_mutation_policy.py` pins the workflow outside
  `ci.yml`/`ci-gate`; the advisory set is named in AGENTS, `docs/ci-local.md`
  and this plan. Revisit conditions are in
  `docs/plan/mutation-testing-spike.md`.
- **P3.2** (#704) **Done.** The last 2 additive cells (`trace-openai-read`,
  `zoo`) graduated into the reviewed baseline (46 -> 48 cells, token/call diff
  in the PR). A new scenario is additive until `make bench-baseline` graduates
  it, or holds a dated record in
  `bench/results/harness-efficiency-additive.json` (issue, reason, ≤30-day
  expiry; graduation prunes it; unrecorded/expired/stale fails). A
  `bench-allow` waiver is `<reason> until YYYY-MM-DD`, capped at 30 days,
  fails closed when undated or expired, is printed in the summary and
  annotated on the PR, and never covers a measurement or additive failure.
- **P3.3** (#705) **Done.** `tests/flake_budget.json` sets the cadence (nightly
  and test-touching PRs; 3 subset repeats; 2 journey repeats) and the numeric
  limits (a quarantined failure above 15% of repeated executions, more than 3
  quarantine entries, or a review older than 30 days is over budget).
  Quarantine entries carry an issue and an `opened` date; release mode refuses
  a stale entry. `make flake-release-check` is the release-candidate gate, and
  #621 is recorded as `known_unmeasured`.
- **P3.4** (#706) **Done.** The coverage recipe now runs the 27 TUI journeys
  after the pty suite, and the TUI floor is the project target: 80% lines
  (measured 82.3% / 88.6% functions in the 0.9 recipe).
- **P3.5** (#707) **Done — decided outcome-only.** The policy
  client supplies no usage counters, so the gate reports `n/a` in token columns
  and claims outcome, tool calls and wall time for this path only. Adding a
  token axis here would require instrumenting the policy client first and is
  post-1.0 work.
- **Exit:** every promoted rule has tests and is pinned in the job inventory;
  the advisory set is named explicitly.

## Decisions required

- Approval of the 0.9 claim and the matrix scope. The P0 seed treats a
  documented command path, visible alias, bundled plugin capability, default
  tool, TUI-only action and the six interface surfaces as the scope; an
  `internal:` cell is a contribution with no user-visible behaviour of its own.
- The P2 profile: local fixed service if available, otherwise the recorded
  cloud `deepseek-chat` stand-in; no service changes.
- #621: recorded as a `known_unmeasured` behaviour in the flake budget; the
  `tab-switch-live` journey is the detector, so a detector failure is
  unquarantined budget spend rather than an accepted pass.
- P3 outcomes: mutation policy, additive-cell graduation, waiver expiry, flake
  budget (**done**), TUI floor (**done**).
- Explicit approval of the stamp and tag.

## Definition of done (P0–P3)

- The matrix and its gate are wired and tested; a capability or journey drift
  is red.
- Every matrix cell has a passing journey or a recorded `na`; a `deferred:` cell
  is a recorded gap that `make journey-matrix-release` refuses.
- A fresh live artifact follows `docs/release-benchmark.md`, covers the
  49-scenario corpus with `--repeat 3`, carries the recorded profile and cost
  bands, and the three deferred validations are executed or explicitly
  reported as not-met.
- The maturity-gate decisions are recorded, and the advisory set is named.
- The flake state at the release commit is the `make flake-release-check`
  verdict: no over-budget run, no stale or overdue quarantine entry, and the
  known unmeasured behaviours (#621) are named in the notes.
- `docs/platform-support.md` has a recorded result for every manual cell the
  0.9 release claims, or the release notes name it as unverified.
- `make upgrade-check UPGRADE_OLD=<0.8.9>` passes on the release candidate.
- No claim of "full coverage" for a cell without a passing journey, and no
  release step taken before its decision is recorded.
