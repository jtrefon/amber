# Plan: 0.9 production pre-release

**Status:** proposed execution plan; no phase has started.
**Milestone:** to be filed as `0.9 readiness` when this plan is approved.
**Scope owner:** benchmark / quality.
**Decision:** 0.9 is a production pre-release gate. 1.0 production-readiness
work starts only after it passes.

## The 0.9 claim

Amber 0.9 is the first build whose user-facing behaviour is measured end to
end on every surface it ships, whose harness cost and agentic behaviour are
pinned against a recorded live run, and whose release artifacts carry that
evidence. It is **not** a 1.0 API freeze; breaking changes remain allowed where
the upgrade note names them.

Each clause maps to evidence: "user-facing behaviour" to the capability matrix
and its journeys; "harness cost and agentic behaviour" to the hermetic gates
plus the P2 live artifact; "release artifacts carry the evidence" to
`make bench-release-check VERSION=0.9.0` and the release checklist.

## Scope and boundary

P0–P3 make **no** version stamp, package-version bump, tag or beta-copy edit.
Release execution is a separate issue (P4), filed when P3 closes; a tag
publishes unattended, so it is never part of a coverage PR.

## What "full coverage" means here

A capability is covered when a **machine-checked manifest** says so, not when a
doc lists it. The manifest is the source of truth; `BENCHMARK.md` and
`docs/spec/tui/e2e-testing.md` link to it rather than duplicating it.

Schema (versioned JSON, path to be chosen in P0.1):

```json
{
  "version": 1,
  "capabilities": [
    {
      "id": "session.resume",
      "source": "completions.json#session.resume",
      "journeys": {"cli": "session-resume", "tui": "restart", "bench": "na: no store in the harness"},
      "notes": ""
    }
  ]
}
```

Rules the gate enforces:

- every documented action in `completions.json`, every bundled plugin
  capability, every tool registered by the default composition, and every TUI
  surface has a capability entry, or an explicit `internal: <reason>`;
- every journey named by an entry exists in the CLI baseline, the TUI runner or
  the long-horizon baseline;
- an `na:` cell records why a surface cannot reach the capability; blank or
  "unknown" is not an answer;
- a new action/tool/plugin/surface without an entry fails, with a documented
  waiver path (reason + expiry) for work that cannot be measured yet.

A journey is what `docs/spec/tui/e2e-testing.md` defines: the real binary, a
loopback endpoint, real tools, workspace/exit/usage/request-contract
assertions. A pty test that renders one screen is not a journey.

## Gaps

1. **The manifest does not exist.** Journeys are scenario-driven; no gate ties
   a user-visible capability to a journey. `test-presence` only requires *some*
   test. Concrete holes: listing-derived capabilities (verbosity, Gemini
   `thinkingConfig`, #686) have unit tests but no binary journey; checkpoint /
   undo and profiles have pty tests but no CLI journey; `/usage` reasoning
   tokens have one pty test, not a journey.
2. **The inventory is stale where it exists.** `BENCHMARK.md` and
   `docs/spec/tui/e2e-testing.md` say 13 TUI journeys; the runner has 14
   (`tab-switch-live` is absent from both tables).
3. **Live validation is stale and narrow.** The local fixed service is
   inviolate and was inactive; the only live minimum is the 0.8.9 cloud
   stand-in. Three promised validations — session brief, 32 KB tool-result
   budget on a live long read, plan/task default-on — are "re-scoped, not
   executed" in `BENCHMARK.md` and `docs/release-benchmark.md`.
4. **Maturity gates are proxies.** `bench-allow:` can waive a regression per
   PR; 25 additive efficiency cells are reported but not gated; mutation
   testing is advisory and selection-sensitive; the TUI coverage floor is
   below the project target.
5. **#621 is unmeasured.** The macOS tab-switch freeze has no reproduction, so
   no journey covers it.
6. **The long-horizon baseline has no token axis.** It records 0 prompt /
   0 completion tokens, so it cannot support a harness-cost claim for that
   path.

## Work plan

Every behaviour change follows red → green. Each work item closes with a PR
whose body records the commands and observed results.

### P0 — A single, machine-checked coverage source

- **P0.1** Define the manifest schema and seed it from `completions.json`, the
  plugin capability registry, the default tool set and the TUI surfaces.
- **P0.2** Add a journey-matrix checker (`tools/journey_matrix_check.py`, new) and wire it in
  the same PR: `tests/gates/`, `tools/gates_manifest.py`, `.github/workflows/ci.yml`,
  `tools/gate_needs_check.py`, and the `make check` / `verify-quick` lists so
  it cannot silently disappear.
- **P0.3** Make one doc the human-readable view; correct the 13-vs-14 counts
  and link the other docs to it instead of copying the table.
- **Exit:** a removed/renamed journey or an unmapped capability turns CI red;
  the gate has its own tests; one doc answers "what is covered?".

### P1 — Close the gaps and validate the run

- **P1.1** Capability journeys: a listing that advertises verbosity and a
  Gemini thinking contract, asserting what reaches the wire and what survives
  a provider switch.
- **P1.2** Journey promotion: checkpoint / undo / rollback and profile
  switching on the CLI; a `/usage` reasoning-token journey asserting
  `(thinking N)` from the real binary.
- **P1.3** #621: a reproducible pty journey from the recording, or a recorded
  0.9 defer signed off by the maintainer; never by silence.
- **P1.4** Live smoke: 3–5 scenarios on the chosen profile plus the 42/42
  harness-integrity floor, to prove the endpoint, corpus and instrumentation
  before the full run.
- **P1.5** Platform matrix: macOS arm64 and Linux x86_64, with the supported
  terminal/multiplexer combinations and which cells are gated vs manual.
- **P1.6** Upgrade path: 0.8.9 → 0.9.0 installed-tree upgrade for config,
  sessions, profiles and packages.
- **Exit:** every manifest cell is a passing journey or a recorded `na`/defer;
  `make agent-eval` and `make tui-agent-e2e REPEAT=2` green.

### P2 — Release-grade live evidence

Follow `docs/release-benchmark.md`; it is the procedure, not a suggestion.

- **P2.1** Run the **49-scenario model corpus** (`--cat model`) with
  `--repeat 3` on the fixed local profile if it is available. The local service
  is inviolate and is never reconfigured. If it is unavailable, use the
  configured cloud profile recorded for 0.8.9 (`deepseek-chat`) and record the
  substitution in the artifact directory and release notes.
- **P2.2** The gate's actual contract, quoted exactly: `mode: live`, engine
  version matching the tag, **≥49 scenarios**, no **unexpected** failures
  (model-quality failures must carry a reason; 0.8.9 had 14), model-score drop
  within **band 5.0** against the previous artifact on the **same (model,
  profile)**. Do not change the profile between 0.8.9 and 0.9, or there is no
  comparable band.
- **P2.3** Cost and behaviour bands on the common corpus, starting from the
  0.8.9 artifact and reviewed before the run: prompt + completion tokens and
  tool calls within +10%, no hard stops, zero compaction failures, and a
  pathology ceiling on TTFT/wall. Record the bands in the artifact README.
- **P2.4** Execute the three deferred live validations (session brief, 32 KB
  tool result, plan/task default-on) or record each as not-met with a reason.
- **P2.5** Redact the artifact and check it for keys/prompts before committing;
  record the cost/approval boundary for the cloud run.
- **P2.6** Re-run policy: one planned run. A repeat needs a recorded reason
  (infrastructure failure, broken scenario, wrong binary) and both runs are
  reported; a low score is a result, not a reason to re-roll.
- **Exit:** `make bench-release-check VERSION=0.9.0` green; `BENCHMARK.md`
  records the run, its profile and its limits.

### P3 — Promote maturity gates deliberately

- **P3.1** Mutation: run a measured per-module/changed-line spike; adopt a
  survivor budget only where the signal is stable, otherwise keep it advisory
  with the selection-sensitivity caveat. Do not put a noisy global score on a
  ratchet.
- **P3.2** Additive efficiency cells: define the graduation rule (reviewed
  baseline update, with the token/call diff in the PR). `bench-allow:` gains an
  expiry and appears in the gate report while active.
- **P3.3** Flake budget: a repeat cadence, a quarantine rule and a maximum
  accepted rate; a known freeze such as #621 counts against it.
- **P3.4** TUI coverage: raise the floor toward the 80% project target, or
  record the accepted gap with a reason and review date.
- **P3.5** Long-horizon token axis: make the baseline record real prompt /
  completion tokens for scenarios that have them, or state that the path is
  outcome-only in the release claim.
- **Exit:** every promoted rule has tests and is pinned in the job inventory;
  the advisory set is named explicitly.

### P4 — Release execution (separate issue)

Out of scope for this plan's PRs. Filed when P3 closes: stamp `0.9.0`; align
`debian/changelog`, `rpm/*.spec` and `homebrew/amber.rb` (sha256 after the
macOS tarball exists); pass `make release-check TAG=v0.9.0`; replace the beta
copy in `website/src/pages/index.astro`,
`website/src/pages/report.astro` and
`website/src/components/AsciiHero.astro`; execute `docs/release-checklist.md` including an `rc`
rehearsal; tag only with explicit approval.

## Decisions required

- Approval of the 0.9 claim and the manifest scope (what counts as a
  capability, and which internals are exempt).
- The P2 profile: local fixed service if available, otherwise the recorded
  cloud `deepseek-chat` stand-in; no service changes.
- #621: repro or recorded 0.9 defer.
- P3 outcomes: mutation policy, additive-cell graduation, waiver expiry, flake
  budget, TUI floor.
- Explicit approval of the stamp and tag.

## Definition of done (P0–P3)

- The manifest and its gate are wired and tested; a capability or journey
  drift is red.
- Every manifest cell has a passing journey or a recorded `na`/defer.
- A fresh live artifact follows `docs/release-benchmark.md`, covers the
  49-scenario corpus with `--repeat 3`, carries the recorded profile and cost
  bands, and the three deferred validations are executed or explicitly
  reported as not-met.
- The maturity-gate decisions are recorded, and the advisory set is named.
- No claim of "full coverage" for a cell without a passing journey, and no
  release step taken before its decision is recorded.
