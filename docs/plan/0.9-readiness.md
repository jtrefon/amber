# Plan: 0.9 production pre-release

**Status:** proposed execution plan; no phase has started.
**Milestone:** to be filed as `0.9 readiness` once approved.
**Scope owner:** benchmark / quality.
**Decision:** 0.9 is a production pre-release gate. 1.0 production-readiness
work starts only after it passes; no stamp, tag or beta-copy edit here.

## Goal and boundary

Promote amber to **0.9** when two things are true and evidenced:

1. **Full end-to-end coverage** — every user-visible capability has a journey on
   every surface where a person can reach it, and the journey inventory is a
   gated fact rather than a doc someone updates by hand.
2. **Mature agentic/harness performance** — the deterministic gates pin the
   harness's cost and behaviour, a fresh live run covers the current corpus,
   and the advisory gates have been promoted or explicitly accepted.

1.0 production-readiness work (`docs/plan/production-readiness.md`) starts
**after** 0.9. No `version.txt` stamp, no tag and no beta-copy edit happens in
this plan. A tag publishes unattended, so each release step is a separate,
explicit decision.

## Gaps

1. **Journeys are scenario-driven, not completeness-driven.** No authoritative
   capability × surface matrix exists, and no gate requires a journey when a
   user-visible capability changes (`test-presence` only requires *some* test).
   Concrete holes: listing-derived capabilities (verbosity, Gemini
   `thinkingConfig`, #686) have unit tests but no binary journey; checkpoint /
   undo and profiles have pty tests but no CLI journey; `/usage` reasoning
   tokens have one pty test, not a journey.
2. **The journey inventory is stale.** `BENCHMARK.md` and
   `docs/spec/tui/e2e-testing.md` say 13 TUI journeys; the binary runs 14
   (`tab-switch-live` is missing from both tables). A coverage claim cannot
   rest on a stale inventory.
3. **Live validation is stale and narrow.** The local inference service is
   inviolate and inactive for live runs; the only live minimum is a cloud
   profile from 2026-11-09. Three promised validations — session brief, 32 KB
   tool-result budget on a live long read, plan/task default-on — are recorded
   as "re-scoped, not executed" in `BENCHMARK.md`.
4. **Maturity gates are still proxies.** `bench-allow:` can waive a regression
   per PR; 25 additive efficiency cells are reported but not gated; mutation
   testing stays advisory and selection-sensitive.
5. **#621 is unmeasured.** The macOS tab-switch freeze has no repro, so no
   journey covers it. It needs a recording or an explicit, recorded defer.

## Execution phases

Each phase closes with a PR whose body records the commands and observed
results. Every behaviour change follows red → green; no phase may be marked
done on a green hermetic run alone where the claim is about live behaviour.

### P0 — Make the inventory authoritative

- Write a capability × surface matrix (CLI, TUI, headless/agent) into
  `docs/spec/tui/e2e-testing.md` and `BENCHMARK.md`; correct the TUI count to
  14 and list every journey by name.
- Add a gate that fails when a journey named in the matrix is absent from the
  runner or its baseline row, and when a production change adds a user-visible
  capability without touching the matrix or carrying a recorded waiver.
- **Exit:** a single doc answers "what is covered?"; a removed or renamed
  journey turns CI red; the 13-vs-14 drift cannot recur.

### P1 — Close the journey gaps

- CLI/TUI journeys for listing-derived capabilities: a provider whose
  catalogue advertises verbosity and a Gemini thinking contract, asserting
  what reaches the wire and what survives a provider switch.
- CLI journeys for checkpoint / undo / rollback and for profile switching;
  promote the existing pty checks to the journey set where a person can reach
  the behaviour.
- One journey for `/usage` with a reasoning-token report, asserting the
  `(thinking N)` readout from the real binary.
- Resolve #621: either a reproducible pty journey from the requested recording
  (terminal app, multiplexer, streaming/reasoning state, frame at freeze), or
  a documented 0.9 defer signed off explicitly — never by silence.
- **Exit:** every matrix cell has a passing journey; no known behaviour is
  unmeasured without a recorded defer; `make agent-eval` and
  `make tui-agent-e2e REPEAT=2` green.

### P2 — Fresh live evidence

- Run the benchmark against the **current** corpus with the current build,
  using the configured cloud profile; the fixed local service stays inviolate.
- Require `mode: live`, `engine_version` matching the candidate version, full
  corpus coverage, zero failed scenarios, and no drop beyond the recorded band
  versus 0.8.9.
- Execute the three deferred live validations (session brief, 32 KB tool result
  on a live long read, plan/task default-on), or record each as not-met with a
  reason. A hermetic result is not a substitute.
- **Exit:** `make bench-release-check VERSION=0.9.0` green with the candidate
  artifact; `BENCHMARK.md` records the run and its limits.

### P3 — Promote the maturity gates

- Decide and record: promote the conservative mutation score to a ratchet, or
  accept it as advisory with the selection-sensitivity caveat; gate the 25
  additive efficiency cells after review; set a review window for
  `bench-allow:` waivers; keep flake-repeat as a nightly signal or make it a
  gating job.
- Add gate tests in `tests/gates/` for every promoted rule and pin it in
  `tools/gates_manifest.py` / `ci-manifest` so it cannot silently disappear.
- **Exit:** the CI job inventory states which gates are gating and which are
  explicitly advisory; `make check` and `make verify-quick` are green.

### P4 — 0.9 release execution

- Only after P0–P3: stamp `0.9.0`, align `debian/changelog`, both `rpm/*.spec`
  and `homebrew/amber.rb` (sha256 after the macOS tarball exists), pass
  `make release-check TAG=v0.9.0`, then execute `docs/release-checklist.md`
  including a `rc` rehearsal.
- Replace beta copy in `website/src/pages/index.astro`,
  `website/src/pages/report.astro` and `website/src/components/AsciiHero.astro`
  in the release commit, with the website build/smoke gates green.
- **Exit:** green `ci-gate` on the release commit, live artifact committed,
  checklist executed end to end, tag explicitly approved.

## Decisions required before P2/P4

- Approval to use the configured cloud profile for the live 0.9 run (no
  changes to the inviolate local inference service).
- Acceptance or defer of #621 for 0.9.
- Which advisory gates become gating at 0.9 (P3), and the `bench-allow` policy.
- Explicit approval of the stamp and tag; a tag publishes unattended.

## Definition of done for this plan

- P0–P3 closed with red/green commits and recorded CI evidence.
- The capability × surface matrix and the journey counts in the docs match the
  runners; a drift is a red gate.
- A fresh live artifact covers the current corpus and all deferred live
  validations are either executed or explicitly recorded as not-met.
- No corner cut: no claim of "full coverage" for a cell without a passing
  journey, and no release step taken before its decision is recorded.
