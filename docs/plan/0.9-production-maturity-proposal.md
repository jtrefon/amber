## 1. The decision in one paragraph

All 0.9 code, gates and journeys are done and `main` is green. The only thing
between us and the 0.9 pre-release is **live evidence**: a committed 0.9 live
benchmark artifact (#700), three live validations (#702), and explicit sign-off
on the recorded #621 defer. `kilocode/free` is a real configured option and the
gateway is reachable, but the token in `~/.config/amber/providers/kilocode.conf`
is rejected (`401 INVALID_TOKEN`) — it needs refreshing before it can be used.
Even with a fresh token, switching profile breaks the score/cost ratchet against
0.8.9 unless we also produce a matched-pair 0.8.9 artifact on the same profile.
**Recommendation:** refresh the Kilocode token, pin one concrete free model,
re-measure 0.8.9 on that exact profile with the released 0.8.9 binary, stamp and
rebuild the 0.9 candidate, then run the 56-scenario corpus with `--repeat 3`.
Tag only after the artifact and all three validations are committed. Keep the
local inference service untouched.

## 3. Why this fits the mission

`docs/spec/MISSION.md` puts the core loop and reliability first, management and
learning later, and makes the user promise *"Your agent runs until it's done"*
and *"Your data stays on your machine. No telemetry, no SaaS."* That promise is
about **product behaviour**: amber must keep working against a local endpoint
and must not phone home. Using a cloud endpoint as a **measurement instrument**
does not change that contract — the 0.8.9 baseline was already a cloud
stand-in, and `docs/release-benchmark.md` explicitly allows a configured cloud
profile when the fixed local service is unavailable, provided the substitution
is recorded. What would violate the mission is shipping a "production maturity"
claim whose live half was never measured, or quietly swapping the comparison
baseline so the ratchet reads green without measuring anything.

The 0.9 claim ("harness cost and agentic behaviour pinned against a recorded
live run") is therefore a truth problem, not a feature problem. No new feature
is warranted here; the work is measurement, matched baselines and honest
documentation.

## 5. Recommended plan and preconditions

### Preconditions (all must hold before the full run)

1. **Valid Kilocode credential.** Refresh the gateway key and update
   `~/.config/amber/providers/kilocode.conf` (or export `AMBER_API_KEY` for the
   run). The key must not be pasted into an issue, PR or artifact. Accept a
   verified chat completion and a balance readout before proceeding.
2. **Pin the model.** Prefer a concrete free id over `kilo-auto/free` so the
   three repeats and the two releases exercise the same model. Candidates seen
   on the gateway include `nvidia/nemotron-3.5-lightning:free`,
   `liquid/lfm-3-1.7b:free` and `nvidia/nemotron-3-ultra-550b-a55b:free`.
   Add a bench profile key (e.g. `kilo-free-pinned`) in `bench/profiles.json`
   and use the same key in both the old and new binary's data root.
3. **Smoke gate.** Run 2–3 scenarios `--repeat 1`, measure wall time, HTTP
   errors, rate limits and score sanity. If the endpoint 401s, throttles or
   drifts model identity, stop and switch to option B.
4. **Matched-pair baseline.** Run the **released 0.8.9 binary** from
   `/tmp/opencode/upgrade-089/amber-0.8.9-linux-x86_64.tar.gz` on the same
   profile/model, `--cat model --repeat 3`, into
   `bench/results/releases/0.8.9/kilo-free-pinned-r3.json`. This is a *new
   measurement of the old release*, not a rewrite of the cloud artifact; its
   README must say so. This restores the score band and the +10 % cost bands
   on the common successful corpus (floor 30; 0.8.9 has 51 scenarios, 0.9 has
   56).
5. **Stamp before the run.** Stamp `version.txt` to `0.9.0`, align
   `debian/changelog`, `rpm/*.spec`, `homebrew/amber.rb`, rebuild **once**, and
   use that binary for every measured run. No mid-run edits.

## 6. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Free endpoint rate limits or long latency over 56×3 scenarios | Smoke first; `--repeat-gap-ms` if needed; record wall/TTFT; escalate to B if a run cannot finish. One planned run; a repeat needs a recorded infrastructure reason and both runs are reported. |
| `kilo-auto/free` routes to different models between repeats | Pin a concrete free id; record it in the artifact and README. |
| Different model family from 0.8.9 makes the score band meaningless | The band is applied only to the matched pair on the same model/profile; the deepseek artifact stays as historical evidence, not a comparator. A deliberate override (`--cost-band`, `--comparable-floor`) is recorded in the release notes. |
| Adding a re-baseline to a past release directory looks like rewriting history | Additive file with a README entry naming the binary, command, date and purpose; the original artifact is untouched. |
| 0.9.0 stamp changes the engine string | Stamp once before the run; no rebuild during measurement; gate checks `engine_version`. |
| A stale token is mistaken for an engine defect | Step 1 verifies auth independently of amber; the 401 is logged as an infrastructure precondition, not a model-quality result. |
| #621 / manual terminal cells remain unverified | Record the deferral sign-off and name the manual cells as unverified in the release record; do not silently close. |
