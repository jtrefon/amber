# Spec: Agent end-to-end testing (pty, CLI and TUI journeys)

Status: implemented (#634, #635, #636, #639, #645, #640; gated by the
`agent-e2e`, `tui-agent-e2e` and `journey-matrix` CI jobs).

Three layers answer different questions:

- the **pty regression suite** (`tests/tui_pty_test.cpp`) pins the interface:
  keys, dialogs, drawers, redraws;
- the **agent journeys** pin the thing a person does with it: prompt → tool →
  edit → answer, through `main()`, the plugin runtime and the real tools;
- the **coverage matrix** (`tests/journey_matrix.json`) pins the claim that
  every user-visible capability is either journeyed on each surface that can
  reach it or carries a recorded reason. It is checked by
  `make journey-matrix` (CI job `journey-matrix`).

No pixel-perfect screen goldens. A journey asserts semantic text, workspace
state, tool calls and the exit path.

The pty is not a terminal emulator. `docs/platform-support.md` is the support
matrix: which terminals are gated by the pty/tmux runs and which need a manual
run. A green pty suite does not prove a specific emulator renders the UI.

## Coverage matrix (0.9)

The journey set is not the coverage claim by itself. The claim lives in
`tests/journey_matrix.json`, and `tools/journey_matrix_check.py` holds it to the
product rather than to a hand-written list. The checker enumerates:

- every documented path in `completions.json`, including the visible aliases;
- every capability a bundled plugin declares, from
  `tests/capability_snapshot.txt` (generated by
  `make capability-snapshot-update` from the live declarations, and pinned by
  `make test`);
- every tool the bare-host default composition registers, from the same
  snapshot;
- every TUI-only `ui.*` action in `menus.json` and `keybindings.json`;
- the six interface surfaces: top rail, drawer, editor, dialog, status bar and
  resource viewer.

A cell is one of:

| Cell | Meaning |
|---|---|
| `<journey>` | a journey the runner can execute; a list when more than one is needed |
| `internal: <reason>` | no user-visible behaviour of its own; covered by the unit/pty layer |
| `na: <reason>` | the surface cannot reach the capability |
| `deferred: #issue <reason>` | a recorded gap; the 0.9 release check refuses every one |

`make journey-matrix-release` is the release variant: the same check with
`--require-complete`, so a `deferred:` cell is red. A removed journey and an
unmapped capability are red in both modes. A pty test that renders one screen is
not a journey and cannot substitute for one in the matrix.

The three surfaces are explicit. **CLI** means `amber-cli` through
`bench/scenarios/e2e/`; **TUI** means the real `amber` binary on a pty through
`tests/tui_agent_e2e_test.cpp`; **bench/headless** means the hermetic harness and
long-horizon scenarios. A capability that a surface cannot reach gets `na:` with
the reason, never a silent blank.

## The pty harness

`tests/pty_harness.h` / `.cpp` own the shared driver:

- `make_isolated_root()` creates a private workspace under the system temp dir
  and sets `AMBER_WORKSPACE` plus the XDG config/state/cache roots. It is
  called before the app starts, so a journey never reads developer state.
- `Tui::start(binary, root)` forks `amber` on a pty. `Tui::raw` is the byte
  stream, `text()` strips ANSI, `pump(ms)` drains, and `wait_for(marker, cap)`
  polls the rendered text. `send()` writes keys.
- `wait_ready(tui, workspace_name)` waits for the startup marker (completions
  loaded, workspace in the status line), not a fixed sleep.
- With `AMBER_EXIT_READY` set, the app writes the exit-ready marker as the last
  thing it does. `Tui::stop()` sends the app's quit path and waits for it; a
  session that has to be SIGKILLed fails the suite, because a killed child never
  flushes coverage. The whole quit path is bounded by
  `AMBER_PTY_EXIT_TIMEOUT_MS` (default 60 s).

The macOS job repeats the TUI journeys twice (`make tui-agent-e2e REPEAT=2`):
each pass is a fresh process, so a plugin-runtime or model-cache static that
survives in-process cannot hide a state leak.

## TUI journeys

`tests/tui_agent_e2e_test.cpp` owns a `Journey` helper: an isolated root, a
loopback `bench::ScriptedEndpoint`, and the pty session. `start()` accepts a
scripted deque or a responder (so a journey can inspect the request and answer
per path), an `extra_settings` string, a `prepare` hook that runs before startup
(skills/MCP/plugins) and `root_api_base` for a versioned dialect.

The 29 journeys are:

| Journey | What it proves |
|---|---|
| `read-edit-verify` | prompt → read → patch → read back → answer; workspace and request count |
| `context` | the second turn sees the first turn's tool result |
| `approval-denied` | a denied bash call still allows the write fallback |
| `approval-allowed` | the dialog's allow path runs the command and writes its marker |

Run them with:

```sh

```

## CLI journeys

`bench/scenarios/e2e/*.json` are the 23 CLI journeys. They are ordinary
scenarios plus `endpoint_replies`/`expected_tools`/`request_log_contains` where
the CLI wire differs from the in-process reference. `bench/binary_driver.cpp`
runs each scenario twice:

1. an **in-process reference** run with the scenario's fake/policy client,
   which supplies the expected tool sequence and statuses;
2. the real `amber-cli` on a loopback endpoint, in an isolated workspace with
   its own XDG roots.

The CLI run must match the final answer, exit code, workspace, token floors,
per-call statuses and tool sequence, and a `request_contract` checked at the
wire (`path`, `tools_include`/`exclude`, `system_prefix_stable`,
`no_system_after_first`). `request_log_contains` asserts a value crossed the
model boundary (a worker report, a skill body, an MCP/plugin result).
`cli_expected_workspace` covers behaviour the in-process reference cannot
reproduce (a cancelled tool leaves no artifact).

| Journey | What it proves |
|---|---|
| `e2e-read-edit-compile` | read → patch → compile → answer; workspace state |
| `e2e-search-two-file-edit` | search finds two files; both edits land |
| `e2e-two-turn-followup` | the second turn sees the first turn's context |
| `e2e-session-resume` | a second process resumes the saved session |
| `e2e-approval-allowed` | an approved bash command runs and writes its marker |
| `e2e-approval-denied-fallback` | a denied bash call still allows the write fallback |
| `e2e-cancel-slow-tool` | `/stop` cancels a slow tool; no partial artifact |
| `e2e-wrong-path-recovery` | a wrong-path error reaches the model and recovers |
| `e2e-compression-mid-task` | `/compress` mid-task preserves the answer and the workspace |
| `e2e-mcp-tool-call` | a real stdio MCP tool runs; its result crosses the wire |
| `e2e-mcp-missing-tool-recovery` | an unknown MCP tool error reaches the model and recovers |
| `e2e-plugin-tool-call` | an external plugin tool runs; its output crosses the wire |
| `e2e-plugin-failure-recovery` | a failing external plugin tool is reported and the turn recovers |
| `e2e-skill-activation` | an authored skill body reaches the model |
| `e2e-skill-missing-recovery` | a missing skill is reported and the turn recovers |
| `e2e-subagent-worker-report` | a delegated worker reports to its owner |
| `e2e-provider-anthropic` | the Messages API path is used |
| `e2e-provider-gemini` | the generateContent path is used |
| `e2e-plan-todowrite` | the plan tool writes the task list and the turn finishes |
| `e2e-background-task` | `process_start` hands a command to the inventory and `tasks list` reads it |
| `e2e-project-index` | `index_add` records a fact and `index_show` reads the index back |
| `e2e-watch-start` | a process watch starts and the one-shot CLI names the still-running task with exit 3 |

```sh
make agent-e2e
make agent-e2e-check     # journeys + the committed token/call/wall baseline
```

`tools/agent_e2e_check.py` fails when a baseline journey is missing or now
fails, when prompt+completion tokens or tool calls grow beyond 10%, or when
wall time exceeds `max(2x + 500 ms, +2000 ms)`. A new journey is additive and
red if it fails. The baseline is regenerated only after review with
`make agent-e2e-baseline`.

## Long-horizon journeys

`bench/scenarios/repo-long/` holds the five multi-module journeys. Each one
applies a real change in a temporary repository and runs its hidden `make test`;
the checker is `make long-horizon-check`, and the committed baseline is
`bench/results/long-horizon-baseline.json`.

| Journey | What it proves |
|---|---|
| `l-01-math` | a wrong arithmetic result is found and fixed; the project's tests run |
| `l-02-text` | a text-processing defect is fixed across the module boundary |
| `l-03-inventory` | an inventory rule is corrected without breaking its consumers |
| `l-04-report` | a report path is repaired and its output verified |
| `l-05-text-followup` | a follow-up turn builds on the previous repository change |

## Adding a CLI journey

1. Add `bench/scenarios/e2e/<name>.json` with `setup`, `prompt`, `fake_replies`
   (and `endpoint_replies` if the CLI wire differs), `oracle`, `checks`,
   `expected_workspace`, `budget` and `platforms`.
2. Run it red: `amber-bench run --driver binary --scenario <name>`. A command
   that cannot reproduce the expected failure is a harness gap, not a test.
3. Fix the harness/engine, then make it green. `make agent-e2e` runs the whole
   `e2e` suite; `--keep-failures` leaves `telemetry.json`, `requests.json`,
   `out.txt` and `err.txt` for a red journey.
4. Run `make agent-e2e-check`; if the journey legitimately changes the token,
   call or wall profile, regenerate the baseline and say why in the PR.
5. The same scenario is part of the `agent-e2e` job; no local-only journey.
6. Name it in `tests/journey_matrix.json` for the capability it covers, and run
   `make journey-matrix`.

For a long-horizon repository journey use `bench/scenarios/repo-long/` and
`make long-horizon-check` (see `bench/scenarios/repo-long/README.md`). The same
matrix rule applies: the five names above are the journeys, not a separate
inventory.

## Adding a TUI journey

1. Add a `journey_<name>` function to `tests/tui_agent_e2e_test.cpp`. Start a
   `Journey` with a scripted endpoint; use `prepare` for skills/MCP/plugins and
   `root_api_base` for a versioned dialect.
2. Wait for semantic markers (`wait_ready`, `wait_for`), never fixed sleeps.
   Approve a dialog by its rendered text; cancel with `/stop`; assert the
   workspace and exit-ready path through `journey.finish`.
3. Run it alone with `AMBER_TUI_JOURNEY=<name> ./tui_agent_e2e_test ./amber`,
   then `make tui-agent-e2e` and `make tui-agent-e2e REPEAT=2`.
4. Name it in `tests/journey_matrix.json` for the capability it covers, and run
   `make journey-matrix`.
5. A TUI journey is not a pty interface test: if it needs a new keybinding or
   dialog, add the interface test in `tests/tui_pty_test.cpp` too.

The CI jobs (`agent-e2e`, `tui-agent-e2e`, `journey-matrix`) are in `ci-gate`;
a red journey or an unmapped capability fails the merge. `make agent-eval` is
the local umbrella for the CLI, policy matrix, trace and long-horizon baselines;
`make preflight` runs it and the TUI journeys.
