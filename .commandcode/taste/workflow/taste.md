# Workflow

- When switching branches to continue PR work, verify the correct branch by checking the open PR with `gh pr view <number>` (e.g., view `headRefName`) rather than assuming the current branch is right. Confidence: 0.8

- Relies on handover/status markdown documents committed in the repo (e.g., in the latest commit) to convey work state; when asked to continue, find and read that doc and propose next steps based on it before diving into fixes. Confidence: 0.7

- Verify external/pipeline state claims against ground truth via `gh` (e.g., PR merge state, repo existence, CI status, branch refs) before making definitive statements; avoid asserting a repo/pipeline fact from prior context or assumption, since a wrong claim causes confusion. Confidence: 0.9

- Thinks in dependency-ordering terms when planning release/packaging steps: recognizes that supporting infrastructure repos must exist/changes land *before* the step that consumes them (e.g., create the Homebrew tap repo before tagging/bumping the version to trigger release). Confidence: 0.75

- Commits use conventional-commit style with a scoped imperative subject line and a detailed body, and include a co-author trailer for bot contributions; stages only source changes (excluding scratch dirs and gitignored binaries). When the user gives a terse approval like "push, PR please", that authorizes the full end-to-end delivery — commit, push, AND open the PR — which the agent executes autonomously (branch naming/base, commit format, PR description), then verifies the PR checks (gh pr checks) started on the new commit. Confidence: 0.9

- When the branch under work has already landed elsewhere (e.g., the topic branch's work was squashed/merged to main as PR #73 while the fix sits on the stale topic branch), expects the fix to be re-based onto the updated main and delivered on its own branch (e.g., `fix/<short-description>` off `origin/main`) rather than committed onto the stale topic branch; unrelated fixes are kept on separate branches from main per the repo's `<type>/<short-description>` convention. Confidence: 0.7

- When asked to prep a release for Homebrew delivery, maps the full gap between the current state and a user-facing upgrade: lists the distinct missing artifacts (version file bump, tagged GitHub release with the darwin tarball, in-repo formula bump plus published tap parity), notes that the auto-bump is broken/manual so a merged PR alone doesn't make `brew upgrade` work, and hands the release back with a "do you want me to do X, or would you rather handle the tag/release?" scoping question before touching anything. Confidence: 0.65

- For a point release, avoids large formatting churn: when replaying a formatter (e.g., clang-format) with a newer version than CI's would rewrite ~1000+ lines of unrelated code, reverts all that churn and keeps only the minimal substantive fix. Reverts with `git checkout -- <files>` and re-applies the single-line change, treating a huge reformat diff as the wrong move for a small release. Confidence: 0.8

- Does not run a C++ formatter over a broad file glob that can capture non-C++ files (e.g., `find ... -name '*.cpp' -o -name '*.h'` plus shell scripts); a formatting pass must be scoped to actual source files, since passing a shell script through clang-format can mangle its syntax and, if committed, break CI (e.g., the `check` hygiene gate). Confidence: 0.7

- Treats a CI gate failure as potentially cascading: after fixing one red job (e.g., `analyze`), waits for the WHOLE pipeline end-to-end (including slow jobs like `lint` and packaging `cd`) before declaring the fix done, because subsequent jobs (`check`, `cd`) commonly reveal independent regressions that surfaced in the same push. Confidence: 0.75

- For technical-debt/quality work on a large codebase, frames the request as a whole-app review for "weak points, slop, dead code, and technical debt" and expects a comprehensive fix proposal before execution: prioritized findings with severity tiers (P0 security first), file:line evidence for every claim, and a suggested landing order — then confirms scope decisions (e.g., cut-vs-wire, deny-vs-gate, implement-vs-remove) before code changes begin. Confidence: 0.8

- Load-bearing audit claims get verified against source before acting on them, and dead-code removal is per-symbol verified (bare unqualified calls included, not just `obj->method` patterns) — earlier sweeping audits are treated as hypotheses that can overcount, not ground truth. Confidence: 0.7

- Treats a green remote CI pipeline as the authoritative completion bar for PR work ("please make sure pipeline is green, use gh to track it"): local green alone is not done when CI-only gates (clang-tidy lint, cppcheck, hygiene checks that don't run locally) can still fail the change; expects the agent to push a branch through a PR, track the runs with `gh`, fix CI-only findings, re-run, and confirm every gate green before declaring done. Confidence: 0.85

- When answering a yes/no question about release/version state ("is the version bumped?"), reports the direct answer up front, then goes ahead and fixes the gap it found (e.g., pushed a stale-tap formula bump and synced the in-repo mirror) rather than stopping at diagnosis. Confidence: 0.7

- Does not leave a broken piece of release automation (an hourly tap auto-bump whose CLI invocation fails every run since the last release) just patched around one-off — calls out the root cause and the durable fix needed in the owning repo (switch from `gh release view latest` to the API `releases/latest` endpoint) so the next release isn't stranded again. Confidence: 0.55

- Verifies claims across sources when outputs conflict or look stale (raw.githubusercontent CDN cache vs. GitHub API vs. git refs), trusting the API/git ground truth over a possibly-cached raw fetch before acting or reporting. Confidence: 0.5

- Holds recent changes to a high bar: a regression from a "recent change" is surprising and unacceptable given the automated test suite is expected to cover it well. Expects changes to ship with test coverage as an explicit guard against regression risk ("we should have test coverage to make sure no regression risks") — when a regression slips through after a burst of related changes (API fix, context handling, a new feature), wants it root-caused against that change timeline and a regression test added so the same failure can't recur, not just patched for the one incident. Confidence: 0.75

- Answers "where should this fix live / will it regress elsewhere" questions with live-verified evidence rather than opinion: probes the real external service (e.g., curl the gateway replaying history with a stray field to confirm it tolerates it, inspects the buffered vs streaming code paths) before asserting whether a fix is provider-specific, model-specific, or client-protocol-level. Claims about another provider's behavior (e.g., "OpenRouter uses 0-based indices so compaction is a no-op there") are hedged as expectations based on spec, not asserted as verified fact. Confidence: 0.6

- Checks on delivery state directly for completed fixes ("did you push your fix? is there PR created?") and expects a plain up-front yes/no on whether the change is committed, pushed, and has an open PR — local uncommitted work is treated as not-yet-delivered, and the agent should report branch/PR status (and any sign-off gating that prevented the push) before offering to proceed. Confidence: 0.55

- The repo's build-hygiene gate (`make check`, tests/build_hygiene.sh) enforces an AGENTS.md audit table of per-file line counts against actual file sizes; when a change grows an audited file (e.g., a new regression test added 39 lines to `tests/run_tests.cpp`), the PR must carry a docs-sync commit updating that count (e.g., `docs: sync AGENTS.md run_tests.cpp audit count (4868 -> 4907)`) — a hygiene job failing on such a drift is a doc-table sync, not a code bug, and the agent fixes it and pushes without asking. Confidence: 0.85

- Audit counts in AGENTS.md are branch-relative: when stashing/moving changes across branches (e.g., a feature branch built on top of an unmerged sibling), the audited line counts must reflect the branch's actual files, not a count that includes the other branch's tests — an incorrectly inherited count causes conflict churn during rebase/merge. Confidence: 0.55

- Responding to a release-prep scoping question with a terse "do everything" (e.g., "do everything, we need new version so i can test it on apple hardware") authorizes executing the ENTIRE release pipeline autonomously and end-to-end without further step-by-step confirmation: release branch with version/formula bump → PR → merge → annotated tag push → waiting out the release workflow until artifacts publish → triggering/verifying the downstream Homebrew tap formula bump → confirming the consumer upgrade path actually resolves. Once delegated this way, the agent runs the whole chain (including release operations like tagging and GitHub Release creation that it may have earlier flagged as possibly user-owned) and reports only at the end. Confidence: 0.85

- Single-message directives that bundle an added feature onto in-flight fix work and end with a version-bump instruction ("please implement your fixes and if possible my request, when finished, push, create PR, when PR pipeline turns green, please increase version so i can test it") pre-authorize the entire delivery chain with no further confirmation: implement the fix and the appended feature together on one branch/PR, verify locally, push, open the PR, watch CI green, then cut the version bump/release for brew testing. The release step is explicitly gated on the PR pipeline being green — the agent should not stop to ask "want me to release?" again after CI passes. Confidence: 0.8

- Terse user statements about a missing capability ("we need ability to add key using TUI/Ncurses window so it never ends in logs") are delegated directives: instead of just diagnosing/explaining, execute the implementation autonomously end-to-end — plan → core + TUI + CLI wiring → tests → PR(s) → merge → verify main green — reporting at the end. Confidence: 0.75

- For cross-cutting features touching core + TUI + CLI (e.g., a new auth/key hook), plans the full design first — exploring the hook seams, thread-boundary/promise machinery, persistence, and 401 landing path in an explicit plan doc before implementation, and confirms UX decisions (e.g., masked single-field dialog vs full settings vs message-only) before writing code. Confidence: 0.65

- When a feature has regressed after repeated failed fix attempts ("you tried to bring it back twice, didnt happen, it is still not there"), expects root-cause investigation BEFORE any implementation: trace the full data flow end-to-end and the git history of the gate/condition to find why prior fixes missed it, because repeated failures signal accumulated code mess/tech debt and a structural cause rather than a one-line symptom. Confidence: 0.9

- For flaky/regressed behavior, treats "it worked before with the same setup" as evidence that a default or gate changed rather than the feature's own logic; when prior fix attempts addressed only the feature's numerics and not the display gate, suspects the root cause is upstream of the symptom (e.g., a visibility condition keyed on a field that defaults to unknown) and hunts the commit that flipped the default before proposing a fix. Confidence: 0.8

- "It regressed" reports on core UX surfaces (e.g., the TUI context gauge) are treated as design-level questions, not just bugs: the investigation is expected to surface a design decision (what to display when the underlying value is unknown) and ask the user to choose the desired behavior with concrete options before implementing. Confidence: 0.7

- Questions that challenge an investigation's logic (e.g., "how can compression work without a window?") are taken as prompts to verify the mechanism's real behavior in code and to check external provider docs/specs, not to be waved off — the user expects the agent to find concrete gaps (e.g., a documented field the parser ignores) and confirm them with live data before asserting a root cause. Confidence: 0.85

- For providers that don't advertise the window, frames the fix as provider-agnostic (parse the standard field every OpenAI-compatible gateway sends) rather than a kilocode special-case, keeping the llama.cpp `n_ctx` shape as priority — so the auto-detected window also re-enables any downstream behavior gated on knowing it (e.g., auto-compression), not just the visible symptom. Confidence: 0.8

- After investigation, confirms the proposed fix scope with the user ("Want me to implement it?") rather than jumping straight into code, even when the root cause is fully confirmed. Confidence: 0.6

- Versioning policy is explicit and semver-lite, stated as a hard rule for the amber repo: no major-version changes for now; a bug fix bumps the PATCH level (0.4.10 → 0.4.11) and a new feature bumps the MINOR/feature level and resets the patch to 0 (0.4.9 → 0.5.0). A release window containing both ships as a minor bump; the bump is chosen by classifying what landed since the last tag, and `version.txt` + the Homebrew formula must always carry the same version. Confidence: 0.95

- Wants the recurring delivery routine (fix/feature work → push → PR → merge only when CI is green → version bump → release + tap sync so brew testing works) recorded as a durable, reusable artifact — e.g., a committed repo-level skill under `.commandcode/skills/<name>/` — rather than improvised per session; the explicit policy details (patch-vs-minor rules, release steps, pitfalls) belong in that artifact so future work follows the same process. Confidence: 0.7

- When the user realizes a reported bug was a false alarm caused by their own misread/mistyped command (e.g., "there was extra word 'effort' that i missed, it was my bad"), they own the mistake openly and expect the agent to roll back/revert anything done under the mistaken request and remove investigation artifacts (temp probe scripts, session logs) so the workspace ends clean — they do not want changes or debris left behind from a moot investigation. Confidence: 0.6

- For large cross-platform/architecture initiatives (e.g., "is it possible to port amber to windows?"), asks for a research-only feasibility investigation before any commitment: no code changes, a structured audit of every platform-coupling point (per-area/file evidence), blockers ranked by engineering effort, realistic paths (e.g., WSL2 vs staged native port), and an honest effort estimate — with the next step offered as a scoping question, not a jump straight into implementation. Confidence: 0.5

- Consult the repo's open GitHub issues via the `gh` CLI when scoping/planning work ("can you check existing issues using gh?"): issue state is treated as ground truth for what's pending, checked with `gh issue list` and details via `gh issue view` rather than assumed from memory or prior context. Confidence: 0.55

- Explicit standing rule for GitHub issue work ("please remember always to update the issue with work you did and close the issue when PR pipeline goes green"): every addressed issue gets a work-done comment on the issue itself at shipping time (red/green commit refs, what changed, verification results), and the issue is closed only when its PR's CI pipeline is fully green — never at implementation time and never on a failed pipeline. The instruction is framed as something to remember and apply to every issue handled, so this housekeeping is expected per-issue and ongoing, not improvised once; an issue whose PR is still draft or has pending/failing checks stays open. Confidence: 0.9
