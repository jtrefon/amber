# Taste
- Prefers retiring legacy/niche platform targets (e.g., Intel macOS builds on over-subscribed legacy CI runners) once the user base shrinks enough that the target "serves no one, causes issues for everyone": maintenance/build/CI burden is weighed against actual usage, and support scope is cut proactively rather than carried indefinitely out of inertia. Confidence: 0.6
- Prefers eliminating external-language runtime dependencies (e.g., Python) from a native C++ codebase — even from test fixtures/tooling — over patching around environment failures. Favors structural fixes (rewrite fixtures in C++, remove the dependency entirely) that make the build/test self-contained and portable across platforms. Confidence: 0.85
- Challenges apparent language/architecture decisions (e.g., "why do we have python in a c++ app?") and expects native, self-contained implementations rather than mixed-language shims that complicate environments. Confidence: 0.8
- For new publishing/infrastructure work (e.g., Homebrew taps/casks, release packaging), prefers reusing prior work as a precedent/template — explicitly references how something was done before ("just as we did for compas") and expects the assistant to inspect that existing repo's structure (via gh) and mirror it rather than design from scratch. Confidence: 0.85
- Treats end-user UX as the ultimate goal, explicitly for a non-technical audience ("we are not building this for us, we are building it for people to use... allow non-technical audience to get engaged"). Evaluates engineering/distribution decisions primarily by how they simplify adoption — e.g., prefers a Homebrew *formula* over a *cask* because formula installs skip Gatekeeper quarantine (the "notarisation bypass": no Apple cert, no right-click override), and wants a one-line URL `curl | bash` installer. Confidence: 0.9
- Explicitly delegates design decisions to the assistant's judgment ("you should know better, use the industry standard and best practices... leave this with you") rather than choosing among presented options; expects the assistant to pick the idiomatic/industry-standard approach and execute autonomously end-to-end. Confidence: 0.85
- Wants user-facing documentation (install instructions, URLs, brew commands) in the main repo's README "for everyone to see" — the place where users actually land — not only in supporting/child repos (e.g., the Homebrew tap README). Confidence: 0.8
- Prefers direct, confirmable answers over verbose narrative delivery: when a long summary is unclear ("your description is unclear"), expects a clear yes/no statement (e.g., "can I brew install now?") before explanation. Confidence: 0.75
- When a version/command/product rename breaks an existing install's upgrade path (e.g., a Homebrew formula renamed to avoid a homebrew-core collision, so `brew upgrade` no longer resolves), wants the migration/recovery steps documented in the relevant README so users who installed the old name can self-serve rather than getting stuck. Confidence: 0.6
- Strongly prefers self-diagnosing, "clean crash with exact reasons shown" over silent or cryptic failures: on missing data/configuration, the app should print a complete report (which file, every searched path annotated with whether each exists [found]/[missing]/[dir exists file missing], the resolved install prefix, the expected location, and a repair hint) directly to stderr, so the user can see where the app looked and where the file should be without reverse-engineering the search logic. Treats a regression in this diagnostic (a previously-working missing-file error becoming silent/cryptic) as a real bug to fix, not a nice-to-have. Confidence: 0.85

- When docs/specs describe an interface the code never actually wires or fires (e.g., a plugin capability/EventBus surface whose registry never calls `capabilities()` and nothing ever publishes events), prefers cutting that dead surface down to the minimal honest scope (lifecycle only) over investing to make the documented-but-unimplemented architecture real. "Smallest honest scope" beats doc-conformance theater. Confidence: 0.7

- Security posture is fail-closed and allowlist-based: chose hard-denying out-of-workspace tool paths (no approval-gated escape hatch for read tools) and inverting a trivially-bypassable command denylist into a read-only allowlist (anything not provably read-only prompts). Expects security controls to be structured so they cannot be silently bypassed rather than patched per-bypass. Confidence: 0.75

- Parser/agent robustness must never turn upstream/foreign-model quirks into hard session failures: an upstream model or gateway (e.g., a provider router emitting 1-based SSE tool-call indices, missing/empty tool names, sparse deltas) may misbehave, but the client must tolerate it — compact/drop malformed tool-call slots at parse finalize so no empty-name call ever reaches dispatch or history replay, since replaying a malformed call poisons the next request (persistent HTTP 400). Graceful degradation at the boundary beats passing the malformed data through. Confidence: 0.7

- Root-cause work on runtime failures should reproduce against the live external service (curl to the real gateway/router with the real wire shape) before concluding where a regression lives; treats "identical to main" diffs as evidence the regression is upstream, then still hardens the client so the upstream quirk cannot surface as a user-visible bug. Confidence: 0.7

- Presses on architectural placement and generality of a fix before signing off: asks which layer should own it (provider vs model vs client/parser) and whether the same failure would regress when the identical model runs through a different provider (e.g., OpenRouter). Expects an evidence-based answer that separates the gateway/transport quirk from the model's own behavior — i.e., a fix keyed to a model id or single provider is fragile (routers change backends per-request), while protocol-level robustness at the client boundary is provider-agnostic and inert for spec-compliant providers. Confidence: 0.55

- Advertised-but-no-op functionality is unacceptable: a UI/command-tree feature that only prints a hint ("not yet implemented", "use /settings instead") should either be implemented for real or removed from the tree entirely — never left as a stub leaf. When both exist, implement the genuinely useful one and drop the redundant hint-only entries. Confidence: 0.7

- Approval-gate UX must be quiet by default: permission requests should be raised ONLY for genuinely destructive/system-wide commands drawn from a curated, JSON-configurable list (rm, dd, git reset, ...). Benign read-only commands (ls, wc) and benign in-workspace writes must run free in write mode — an allowlist that prompts on anything not provably read-only is treated as broken, not as a safety feature. Confidence: 0.9

- Approval grants must actually stick and be scope-precise: "always allow" / "allow session" on a command kind must suppress later requests for that same kind (never a double request for the same resource), while granting one destructive kind (rm) must not silently cover a different one (dd). Persisted rules that are stored but never consulted at the gate are a real bug ("when i grant always, it rises it again"). Confidence: 0.9

- Reports bugs by pasting the raw terminal/app error verbatim ("here is the error we got: error: chat probe failed: HTTP 400 from LLM server: ...") and expects the assistant to diagnose from that paste, including mining the on-disk session logs (`.amber/logs/*.jsonl`) for the exact request/error sequence when the paste is ambiguous. Confidence: 0.8

- When offered a choice between hardening the client (code change + regression test + PR), making no code change (upstream-only), or investigating further, picks the code-change option and expects the assistant to proceed autonomously through test-first implementation, CI green, and PR. Confidence: 0.7

- Expected access-mode model for the agent: READ = read-only tools only, never writes; WRITE = full freedom inside the sandbox except destructive commands, with per-folder approval for anything outside the sandbox; YOLO = everything runs with no prompts. Mode boundaries should be conveyed to the model via system-prompt text. Confidence: 0.85

- Measures whether a release "is bumped" by the consumer upgrade path actually resolving the new version (e.g., `brew upgrade` pulling it), not by the git tag or GitHub Release existing: a released version that the Homebrew tap formula hasn't caught up to (auto-bump silently failing) is treated as not released for the user. Expects release state to be checked end-to-end across version file, tag, release assets, and published formula parity. Confidence: 0.7

- The user's own verification loop for merged fixes is `brew upgrade` on their Apple hardware ("we need new version so i can test it on apple hardware"): they consume releases through the Homebrew tap rather than building from source, so a merged fix is only usable to them once a versioned release with the darwin arm64 artifact and matching tap formula is actually live. Requests framed as "I need a new version to test" should therefore drive a full release cut, with the darwin arm64/brew path verified end-to-end, not just a version-file bump or a merged PR. Confidence: 0.9
- API-key/secret flows must keep credentials out of chat transcripts and logs entirely: keys are captured via a masked form and persisted to the per-provider config file (`~/.config/amber/providers/<name>.conf`, which overlays the built-in preset) plus the global config — never entered as chat text or leaked into the LLM request context. Key persistence is a per-provider domain concern that must survive restarts and apply across CLI and TUI. Confidence: 0.8

- A single shared, provider-agnostic mechanism is preferred over per-provider special cases for anything keyed to provider quirks: an auto-router (e.g., kilo-auto/free) can change backend per request, and the same model behaves differently behind a different gateway — so auth/key prompting, retry classification, and malformed-tool-call handling are built once at the client/hook layer and apply uniformly to kilocode, openrouter, custom, and saved .conf providers alike. Confidence: 0.6

- When a reported regression turns out to have no code diff (the feature code exists and is byte-identical to the last good version), verifies what the user actually did (session/prompt history) and whether the capability is reachable from the command they used — a "we had it, now it doesn't work" report can be a discoverability/reachability gap (capability moved behind a deeper menu surface), not removed or broken code. Confidence: 0.6
